## 0. 背景与目标

当前循环的三个问题：

1. **比赛没有玩家参与**。[simulateMatchCore](../../../app.js) 在 `advanceMonth` 内部一次跑完，玩家只能看简报。
2. **反馈周期太长**。赛季目标（[makeSeasonGoal](../../../app.js)）只在 18 岁以后生效，且一年才结算一次；16 岁以前完全没有目标反馈。
3. **月度行动趋同**。每月固定 3 点、月底清零、同种行动 `max:2`，最优解很快固化成同一套点法。

目标：让玩家觉得「这场球是我踢出来的」，把反馈周期从一年压缩到三场，并让训练产生长期身份差异。

**实施分四期，每期独立可玩、独立提交**：

| 期 | 内容 | 本文档章节 |
|---|---|---|
| 1 | 减少重复点击 | §4 |
| 2 | 三场挑战 | §3 |
| 3 | 月度循环重构 + 比赛互动 | §1、§2 |
| 4 | 流派成长 | §5 |

第 3 期的架构改动（§1）必须先于比赛互动（§2）完成，两者同期交付。

### 0.1 分期依赖与降级

后期功能被前期引用的地方，前期一律走降级分支，**不留半成品代码**：

| 引用点 | 第 4 期前的行为 |
|---|---|
| §2.5 场景触发条件中的「流派 ≥1」 | `styleLevel()` 恒返回 0，条件视为不满足；`box_scramble` / `through_ball` 靠 `matchPlan` 条件仍可触发，`aerial_duel` 靠身高条件仍可触发 |
| §2.5 标记 `[Lv2]` 的选项 | 不出现。每个场景至少有 3 个非 Lv2 选项，玩法完整 |
| §2.4「对应流派经验 +5」 | 跳过 |

## 1. 前置架构改动：月度循环续延化

### 1.1 现状

`advanceMonth(force)` 是一条同步直线：

| 行为 | 说明 |
|---|---|
| A 段 | `modalBusy=true`；月份 +1、执行点重置、体能/状态回复、身高、工资、被动收入、16 岁分流、18 岁转职 |
| B 段 | `shouldPlayMatch()` → `simulateMatchCore` → `applyMatch` → `queueMatchReport` |
| C 段 | 伤停/禁赛递减、两月随机事件、半年剧情、报价刷新、国家队与世界杯、赛季结算（含 `applyAging`、`evaluateSeasonGoal`、`seasonAwardCheck`、`makeSeasonGoal`）、风险结算、分手检查、成就、排行 |
| D 段 | 月度小结入队（`modalQueue.unshift`）、退役检查、`modalBusy=false`、`saveGame`、`renderAll`、`pumpModal` |

比赛一旦需要玩家点击，B 段就会跨越多个事件循环，C/D 段必须延后。

### 1.2 目标结构

```
advanceMonth(force)
  ├─ 守卫（S 存在 / 非 modalBusy / 未退役 / 执行点确认）
  ├─ modalBusy = true
  ├─ [A 段]
  ├─ ctx = { snap, preSusp, preInjury, justTurned16, matchReportModal:null }
  ├─ shouldPlayMatch(S) ? startMatchFlow(S, ctx) /* 提前 return */ : finishMonth(ctx)

startMatchFlow(s, ctx)
  ├─ pending = prepareMatch(s)
  ├─ s.pendingMatch = { pending, ctx, index:0 }   // 持久化，供中断恢复
  ├─ !pending.plays ? resolveMatch(s) : (modalBusy=false, stepKeyMoment(s))

stepKeyMoment(s)
  ├─ pm = s.pendingMatch
  ├─ pm.index >= pm.pending.moments.length ? resolveMatch(s) : 弹出第 index 个关键时刻
  └─ 每个选项 apply: 记录选择 → pm.index++ → saveGame() → setTimeout(()=>stepKeyMoment(s), 0)

resolveMatch(s)
  ├─ modalBusy = true
  ├─ report = finishMatch(s, pm.pending)
  ├─ applyMatch(s, report)
  ├─ challengeProgress(s, report)          // §3
  ├─ ctx.matchReportModal = buildMatchReportModal(report)
  ├─ s.pendingMatch = null
  └─ finishMonth(ctx)

finishMonth(ctx)
  ├─ [C 段]
  ├─ modalQueue.unshift(月度小结)
  ├─ ctx.matchReportModal && modalQueue.unshift(ctx.matchReportModal)   // 简报排到小结之前
  ├─ [D 段] 退役检查
  └─ modalBusy = false; saveGame(); renderAll(); setTimeout(pumpModal, 0)
```

### 1.3 三个必须处理的细节

**弹窗顺序反转（已确认）**
现为 `月度小结 → 比赛简报 → 事件`，改为 `比赛简报 → 月度小结 → 事件`。
实现：`queueMatchReport(s, report)` 拆成纯函数 `buildMatchReportModal(report)`（返回 modal 对象，不入队），由 `finishMonth` 在 unshift 月度小结**之后**再 unshift 简报。

**中断恢复**
`pumpModal` 的 `finally` 每次点击都调用 `saveGame()`。若玩家在两个关键时刻之间关闭页面，会存下「月份已 +1、比赛未结算、C 段未执行」的坏档——若恰好是 `totalMonth%12===0` 的月份，将整季跳过赛季结算与年龄衰退。

解决：`S.pendingMatch` 全程持久化，且必须是纯 JSON 数据（不含函数、不含 DOM 引用）。
- `pending`：`{opponent, home, starts, plays, role, clubEdge, gf, ga, goals, assists, keyWins, failures, timeline[], injuredInMatch, momentIds[], choices[], plan, talentBonus, competition}`
- `ctx`：`{snap, preSusp, preInjury, justTurned16}`（`matchReportModal` 不入档，恢复时重建）
- 启动流程（`boot()` 中 `loadGame()` 成功后、`renderAll()` 之前）检测 `S.pendingMatch` → 调用 `resumeMatchFlow(S)`，直接跳回 `stepKeyMoment`。

**modalBusy 竞态**
`resolveMatch` 开头置 `modalBusy=true`，确保 `buildMatchReportModal` 与 `finishMonth` 的入队动作不会被 `pumpModal` 抢先消费；`finishMonth` 结尾统一 `modalBusy=false` + `setTimeout(pumpModal, 0)`。
`setTimeout` 是必需的：`finishMonth` 可能在 `pumpModal` 的点击回调栈内被调用，而该回调的 `finally` 会同步执行 `mask.classList.add("hidden")` 与 `modalBusy=false`，直接同步 `pumpModal()` 会被这段 `finally` 关掉。现有代码已有同样的规避（`option("放弃剩余时间", …, ()=>setTimeout(()=>advanceMonth(true),120))`）。

### 1.4 不在本次范围

国家队比赛（`simulateNationalMatch`）与世界杯（`wcMatchSim`）**保持非交互**。世界杯已有逐场「基调选择」，不再叠加关键时刻。

## 2. 比赛互动

### 2.1 赛前职责（常驻设置）

`S.matchPlan ∈ {"box","deep","press"}`，**强制三选一，无中立档**。
在行动页以三张卡片展示，点击即切换，**不消耗执行点**，切换后一直沿用。
新档初始值与老档 normalize 值均为 `"box"`（前锋本职）。

| id | 名称 | 效果 | 依赖属性 |
|---|---|---|---|
| `box` | 专注禁区 | 进球转化 +0.08；助攻转化 −0.10；自动回合的 `types` 池去掉 `pass`、`finish` 加权 ×2 | 射术 |
| `deep` | 回撤组织 | 助攻转化 +0.10；进球转化 −0.06；**评分随机项从 ±0.48 收窄到 ±0.30** | 视野 |
| `press` | 疯狂逼抢 | `clubEdge` +2.5；赛后体能额外 −6；`injuryChance` ×1.6 | 耐力 |

### 2.2 关键时刻流程

- 仅在 `pending.plays === true` 时触发，每场 **2 个**。
- `prepareMatch` 在现有 `attempts` 循环中**预留 2 个名额**（即 `attempts` 减 2，最少保留 1 个自动回合），其余回合照旧自动模拟，先算出基线 `gf/ga/goals/assists/timeline`。
- 第 1 个关键时刻从「分钟 10–70」的候选池抽，第 2 个从「分钟 55–88」抽，两者 id 不同。
- 第 2 个时刻若此时球队落后则强制 `late_chase`，领先则强制 `defend_lead`，平局才走常规抽取。
  **`late_chase` 与 `defend_lead` 只通过这条强制路径出现，不参与常规候选池抽取。**
- **兜底**：若某个时段的候选池为空，退化为 `wing_duel`（无触发条件、分钟 15–80，同时覆盖两个时段）。抽取逻辑必须保证任何属性/职责组合下都能凑齐 2 个时刻。

### 2.2.1 `simulateMatchCore` 的去向

`simulateMatchCore(s, rng, opts)` **保留为非交互包装器**，不删除：

```js
function simulateMatchCore(s, rng=Math.random, opts={}){
  const pending = prepareMatch(s, rng, opts);
  return finishMatch(s, pending, rng);   // 未作答的关键时刻按「稳妥选项」自动判定
}
```

理由有三：
1. [tests/structure.test.mjs:79](../../../tests/structure.test.mjs) 直接调用它跑 40 场统计，签名与返回值必须保持稳定。
2. `未出场` / `替补未登场` 的比赛走同一条路径，无需重复实现。
3. 未来若要加「快速模拟」按钮，直接复用。

拆分后的三个函数：

| 函数 | 职责 | 纯度 |
|---|---|---|
| `prepareMatch(s, rng, opts)` | 抽对手、判首发/出场、算 `clubEdge`、掷基线比分、跑自动回合、抽 2 个关键时刻剧本 | 返回纯 JSON 对象，**不修改 `s`** |
| `finishMatch(s, pending, rng)` | 结算关键时刻选择、修正 `gf/ga/goals/assists/rating`、排序时间线、组装 report | **不修改 `s`**（体能/伤病等仍由 `applyMatch` 施加） |
| `applyMatch(s, report)` | 维持现状 | 修改 `s` |

### 2.3 成功率公式

```js
p = 0.35
  + (关键属性 - 对手实力) * 0.008   // 每 1 点差值 = 0.8 个百分点
  + form    / 1000                  // 状态 ÷10 个百分点
  + fitness / 2000                  // 体能 ÷20 个百分点
  + 天赋加成
  + 风险修正
p = clamp(p, 0.15, 0.85)
```

**关键属性**取值：`finishing / dribble / vision / setPiece / height / speed / burst / stamina / will`，由选项声明。
**对手实力**取 `pending.opponent.strength`。

天赋加成：

| 天赋 id | 条件 | 加成 |
|---|---|---|
| `box_instinct` | 关键属性为 `finishing` | +0.06 |
| `explosive_start` | 关键属性为 `dribble` 或 `burst` | +0.06 |
| `aerial_king` | 关键属性为 `height` | +0.08 |
| `free_kick` | 关键属性为 `setPiece` | +0.10 |
| `big_heart` | 场景分钟 ≥80 或球队落后 | +0.05 |
| `football_iq` | 关键属性为 `vision` | +0.05 |

风险修正：`稳妥 +0.08` / `常规 0` / `高风险 −0.15`。

流派加成另计，见 §5.3。

### 2.4 成败后果（不对称）

**成功**
- `goal` 类：`goals++`，`gf = Math.max(gf, goals)`；评分加成按选项
- `assist` 类：`assists++`，`gf = Math.max(gf, goals+assists)`
- 评分加成 +0.15 ~ +1.20（按选项）
- `keyWins++`
- 对应流派经验 +5（§5）
- 部分选项额外给 `coachFavor`

**失败**
- 评分惩罚 −0.10 ~ −0.60（按选项）
- `failures++`
- **高风险选项（风险修正 −0.15）失败时，35% 概率触发对手反击：`ga++`，时间线追加一条 `kind:"bad"`**
- 部分选项额外扣体能

`pressure_proof` 天赋使评分惩罚减半（与 `applyMatch` 现有用法一致）。

## 3. 三场挑战

### 3.1 定位

与赛季目标**共存**。赛季目标仍是有降薪/雪藏硬后果的教练 KPI；三场挑战是短反馈层，奖励小而频繁。

**16 岁起开启**（`ageInfo(s).age >= 16`）。14–15 岁梯队期每 3 个月才一场球，开启后反馈周期反而更长。

### 3.2 数据结构

```js
S.challenge = {
  id: "c1722…",           // 唯一
  tier: "steady"|"attack"|"daring",
  kind: "avgRating"|"starts"|"noLow"|"contrib"|"keyGoal"|"braceGA"|"goals"|"highRating"|"winStreak",
  target: 6.8,
  text: "三场平均评分达到6.8",
  played: 0,              // 已计入的出场数，满 3 结算
  acc: { ratings:[], starts:0, goals:0, assists:0, keyGoals:0, braces:0, wins:0, streak:0 }
}
```

### 3.3 生成与结算

- **生成**：`advanceMonth` 的 A 段，若 `age>=16 && !S.retired && !S.challenge`，调用 `makeChallenge(s)` → 弹「教练挑战」三选一弹窗（`enqueueDecision`），玩家选定后写入 `S.challenge`。
- **推进**：`challengeProgress(s, report)` 在 `applyMatch` 之后调用。**仅 `report.role !== "未出场"` 的比赛计入 `played`**——伤停或坐板凳不消耗挑战场次，避免伤病死亡循环。
- **结算**：`played === 3` 时判定成败，发放奖惩，`S.challenge = null`，下个月生成新挑战。
- 挑战**不会过期**。长期伤停期间进度冻结。

### 3.4 三档目标与奖惩

每档从 3 个目标中随机取 1。

| 档 | 目标池 | 成功奖励 | 失败 |
|---|---|---|---|
| **稳妥** steady | `avgRating` 三场平均评分 ≥6.8<br>`starts` 至少两场首发<br>`noLow` 三场都不出现低于 6.0 的评分 | 教练信任 +4，状态 +3 | 状态 −2 |
| **进攻** attack | `contrib` 三场制造 2 个进球（进球+助攻）<br>`keyGoal` 至少打进 1 个关键进球<br>`braceGA` 完成一次单场传射 | 声望 +3，教练信任 +6，奖金 = `max(5, round(salary*1.5))` 万 | 状态 −3 |
| **冒险** daring | `goals` 三场打进 3 球<br>`highRating` 至少获得一次 8.5 分<br>`winStreak` 帮助球队取得三连胜 | 声望 +6，教练信任 +10，奖金 = `max(12, round(salary*3))` 万<br>*（第 4 期起追加：流派经验 +15，给当前经验最高的流派）* | 状态 −4 |

**失败一律不扣教练信任**。输球本身已经在 `applyMatch` 里扣信任，再叠加会形成越输越难的死亡循环。

**关键进球**定义：该场存在玩家进球，且 `进球分钟 >= 75` 或 `Math.abs(gf - ga) <= 1`。

## 4. 减少重复点击

### 4.1 同月重复训练递减

保持 `max:2` 不变。同一行动**本月第二次**执行时：

- 属性/技能收益 ×0.6
- 流派经验 +6（而非 +10）
- `fatigueInjuryCheck` 的 `base` ×1.5

**实现**：模块级变量，不写入存档。

```js
let actionMult = 1, actionInjuryMult = 1;   // 模块顶层，默认 1
// gainStat / gainSkill：n *= actionMult
// fatigueInjuryCheck：base *= actionInjuryMult
```

`applyAction` 中：

```js
const repeat = used >= 1;
actionMult = repeat ? 0.6 : 1;
actionInjuryMult = repeat ? 1.5 : 1;
try { a.run(s) } finally { actionMult = 1; actionInjuryMult = 1 }
```

用模块级变量而非 `S` 上的字段，可避免污染存档；默认值 1 保证事件、剧情、测试直接调用 `run()` 时行为不变。

行动卡按钮文案：已执行 1 次时显示 `再练一次 · 收益60%`。

### 4.2 行动组合奖励

`S.combosHit = []`（本月已触发的组合 id，月初清空）。
每次 `applyAction` 结束后调用 `checkCombos(s)`；命中则 `toast` + `log(s,"good",…)`，每月每种只触发一次。

| id | 名称 | 触发条件（第 4 期后） | 触发条件（第 1–3 期） | 奖励 |
|---|---|---|---|---|
| `sci_train` | 科学训练 | `train_burst` 或 `train_target` + `recover` | `train_body` + `recover` | `injury.risk −8`，体能额外 +5 |
| `goal_study` | 门前研究 | `train_box` + `train_play` | `train_tech` + `train_team` | 第 4 期后：禁区杀手 +8、组织型 +8 经验<br>第 1–3 期：射术 +0.3、视野 +0.3 |
| `life_balance` | 生活平衡 | 任一训练 + `love_time` | 同左 | 状态 +4，感情 +4 |
| `star_effect` | 明星效应 | `media` + `S.matches[0]` 存在且 `rating >= 7.5` | 同左 | 补发 `fame +5`（等于 `media` 行动本身的 `fame` 收益，效果即翻倍） |

组合判定读取一份 `COMBOS` 常量表，训练 id 写成数组（`any:[…]` / `all:[…]`），第 4 期只需替换数组内容，不改判定逻辑。

### 4.3 未用点自动休息

改写 `advanceMonth` 的执行点确认弹窗（现文案：「这些点用不完也不会留到下个月」）：

> 本月还剩 **N** 点。放弃剩余时间将自动休息：**体能 +6N，伤病风险 −3N**，但不会获得属性成长。

选项「放弃剩余时间」改为「休息，进入下个月」。
A 段实际结算：`change(s,"fitness", 6*n)`；`s.injury.risk = Math.max(0, (s.injury.risk||0) - 3*n)`。

## 5. 流派成长

### 5.1 数据结构

```js
S.styles = { box:0, burst:0, target:0, play:0 }   // 经验值
```

等级：`styleLevel(exp) = exp>=120 ? 3 : exp>=60 ? 2 : exp>=20 ? 1 : 0`
**四条线各自累积，互不排斥**。执行点稀缺自然形成专精，不做硬锁。

### 5.2 训练行动改造（3 个 → 4 个）

删除 `train_body`、`train_tech`、`train_team`，新增 4 个专项训练。`phases` 均沿用原有的 `["academy","firstteam","overseas","campus","pro"]`，`max:2`。

| id | 名称 | 流派 | 属性收益 | 体能 | 伤病 | 其他 | 出处 |
|---|---|---|---|---|---|---|---|
| `train_box` | 抢点终结 | `box` | 射术 +.75、定位球 +.50、意志 +.22 | −10 | — | — | 原技术训练 |
| `train_burst` | 速度突破 | `burst` | 速度 +.70、爆发 +.62、盘带 +.40 | −13 | `.022` | — | 原身体训练 |
| `train_target` | 对抗支点 | `target` | 身高 +.55、耐力 +.60、意志 +.30 | −13 | `.022` | — | 原身体训练 |
| `train_play` | 回撤组织 | `play` | 视野 +.62、盘带 +.35、定位球 +.30、射术 +.15 | −6 | — | **教练信任 +3、状态 +3**，保留 `training_rat` 天赋触发 | 原合练与复盘 |

设计说明：
- 原身体训练一次给 速度 +.55 / 爆发 +.50 / 耐力 +.35 / 身高 +.30，拆成两个行动后单点收益上调，避免物理属性整体被砍。
- 教练信任的稳定月度来源挂在 `train_play` 上，不随拆分丢失。
- 每月总产出仍受 3 个执行点封顶，本次改动只改变**成长方向的可控性**，不改变总量。

**经验获取**（穷举，无其他来源）：
- 执行对应专项训练：+10（同月第二次 +6，见 §4.1）
- 比赛中成功使用带该流派标签的关键时刻选项：+5
- 「门前研究」组合：禁区杀手 +8、组织型 +8（§4.2）
- 冒险挑战达成：+15（§3.4）

`street`（去踢野球）、`campus_match`（校队强化赛）、`national_role`（适应多位置）虽然也涨技术属性，但**不给流派经验**——流派代表刻意练习的踢法，不是所有触球都算。这四个专项训练是唯一的日常经验来源。

### 5.3 流派效果

| 流派 | 一级（20 exp） | 二级（60 exp） | 三级（120 exp） |
|---|---|---|---|
| **禁区杀手** `box` | 关键属性为 `finishing` 的选项 `p += 0.05` | 解锁「抢前点」（`box_scramble`） | 球队落后时触发的 `late_chase` 中，射门类选项再 `p += 0.08`，且成功进球的评分加成再 +0.30 |
| **爆点前锋** `burst` | `counter_break` / `press_trigger` 场景内所有选项 `p += 0.06` | 解锁「强行突破」（`counter_break`） | 关键属性为 `dribble` 的选项成功后，额外 `chance(0.12)` 追加一个进球 |
| **支点中锋** `target` | `aerial_duel` 进入候选池的权重 ×1.5 | 解锁「背身护球」（`hold_up`） | 该流派标签的选项成功后必定触发「队友进球判定」（覆盖选项声明） |
| **组织型** `play` | 助攻转化率 +0.08（自动回合与关键时刻同时生效） | 解锁「回撤直塞」（`through_ball`） | `clubEdge += 2` |

禁区杀手三级不改变**哪个场景**被触发（落后时强制 `late_chase` 是 §2.2 的通用规则），只改变该场景内射门类选项的成功率与回报——这就是「落后时更容易获得绝杀机会」。

### 5.4 与天赋的关系

天赋代表出生特质，流派代表后天踢法，**两者独立、不合并**（明确要求）。
生涯页拆成两张卡片：「天赋」（现有 `talentMini` 迁移）与「流派」（新增）。

### 5.5 界面

生涯页（`renderCareer`）现有「技术属性」卡片下方新增一张流派卡片：

- 四条线各一行：名称、等级徽章（`—/Ⅰ/Ⅱ/Ⅲ`）、经验进度条（复用 `.bar-wide`）、当前已生效效果的一句话
- 未达一级的路线灰显

不新增导航 tab（导航已有 9 项，手机端已需横向滚动）。

## 6. 存档兼容

**不升 `VERSION`**（保持 `2`）。[loadGame](../../../app.js) 内新增 `normalizeSave(data)`，在 `return data` 之前补齐新字段：

```js
function normalizeSave(d){
  d.matchPlan = ["box","deep","press"].includes(d.matchPlan) ? d.matchPlan : "box";
  d.styles = Object.assign({box:0,burst:0,target:0,play:0}, d.styles||{});
  if(d.challenge === undefined) d.challenge = null;
  if(d.pendingMatch === undefined) d.pendingMatch = null;
  if(!Array.isArray(d.combosHit)) d.combosHit = [];
  return d;
}
```

- 被删除的三个旧训练 id 残留在 `actionUsage` 中无害：`renderActions` 按 `ACTIONS` 过滤，旧 id 不会渲染；`applyAction` 找不到定义会直接 `return`。
- 老档流派经验从 0 起算，不追溯补偿。
- 老档 `matchPlan` 默认 `"box"`，玩家可随时在行动页改。

`createInitialState` 同步新增上述五个字段。
